# DDD Part I: Putting the Domain Model to Work

## Knowledge Crunching (Ch.1)

The iterative, collaborative process where developers and domain experts refine chaotic domain
information into a practical model.

### Core Concepts

- **Knowledge Crunching** — "Effective domain modelers are knowledge crunchers." Not a one-time
  activity but a continuous iterative process of distilling domain knowledge into a model.
- **Continuous Learning** — Teams consciously grow knowledge about both technical and domain-specific
  subjects through stable core members.
- **Knowledge-Rich Design** — Objects have behavior and enforce rules; the model is not just a data
  schema but integral to solving complex problems.
- **Deep Models** — Constant refinement forces developers to learn true business principles;
  abstractions reflect deep knowledge of the business rather than surface-level mechanics.

## Communication and the Use of Language (Ch.2)

- **Ubiquitous Language** — A shared vocabulary used consistently across developers, domain experts,
  and code. Reflects the domain model and evolves as gaps appear.
- **Modeling Out Loud** — Refining understanding through spoken discussion, exploring language
  alternatives, translating insights to diagrams and code.
- **One Team, One Language** — Ensuring domain experts and developers speak the same vocabulary to
  quickly identify model inadequacies.
- **Documents and Diagrams** — Complement code and conversation, not duplicate what code already
  expresses.
- **Written Design Documents** — Minimal documentation that tells a story about the model.
- **Executable Bedrock** — The code itself as the ultimate design document.
- **Explanatory Models** — Models used purely for teaching/communication, separate from the
  implementation model.

## Binding Model and Implementation (Ch.3)

- **Model-Driven Design** — Tightly binding the code implementation to an underlying domain model;
  software constructs mirror model concepts.
- **Modeling Paradigms** — Object-oriented being the dominant paradigm Evans discusses, plus
  discussion of non-OO paradigms.
- **Hands-On Modelers** — Developers must participate in model discussions and understand how code
  changes affect the model. Separation of modelers from implementers is rejected.
- **Letting the Bones Show** — Making the structural choices of the model visible in the code.

# DDD Part II: The Building Blocks of a Model-Driven Design

## Isolating the Domain (Ch.4)

### Layered Architecture

Separation into distinct layers with clear boundaries:

| Layer | Responsibility |
|---|---|
| **User Interface / Presentation** | Shows information to user, interprets user commands |
| **Application** | Thin layer coordinating tasks, delegates to domain. Does NOT contain business rules or domain knowledge. No state reflecting the business situation |
| **Domain** | The heart of business software. Represents business concepts, rules, and situations. State reflecting the business situation is controlled here |
| **Infrastructure** | Provides generic technical capabilities: persistence, messaging, drawing for UI, etc. |

### Anti-Patterns

- **Smart UI Anti-Pattern** — Putting all business logic into the user interface. Acknowledged as
  sometimes appropriate for simple projects but antithetical to DDD.

### Other Isolation Strategies

- Evans acknowledges alternative isolation strategies beyond classical layering (e.g., Hexagonal
  Architecture, as later championed by Vernon).

## A Model Expressed in Software (Ch.5)

### Associations

Simplifying relationships through:

1. **Imposing a traversal direction** — Directional bias; eliminate bidirectional when possible
2. **Adding a qualifier** — Reduce multiplicity (e.g., many-to-many → one-to-many)
3. **Eliminating non-essential associations** — Remove relationships not needed by current model

### Entities (Reference Objects)

Objects defined primarily by **identity continuity** across their lifecycle rather than attributes.

- **Identity** — A unique identifier that persists; may be natural (e.g., SSN) or surrogate (generated)
- **Continuity** — The entity persists through time and different states
- **Identity Operations** — Establishing clear mechanisms for distinguishing entities

#### Identity Strategies (Vernon's extension)

| Strategy | Description |
|---|---|
| User-provided | Business-meaningful identity (e.g., ISBN, SSN) |
| Application-generated | UUID/GUID generated by the application |
| Persistence-generated | Database sequences or auto-increment |
| Other BC-supplied | Identity from another Bounded Context |

- **Surrogate Identity** — ORM-specific identity distinct from domain identity
- **Identity Stability** — Identity should not change once assigned

### Value Objects

Objects lacking conceptual identity, defined only by their attributes.

- **Immutability** — Value objects should be immutable; all methods are queries
- **Equality by Value** — Two VOs are equal if all their attributes are equal
- **Replaceability** — A VO can be freely replaced by another with the same values
- **Side-Effect-Free Behavior** — All operations return new value objects rather than modifying state
- **Conceptual Whole** — A VO models a single cohesive concept
- **Sharing and Copying** — Immutability enables safe sharing; copying when mutability is needed
- **Measures, Quantifies, or Describes** — The three roles of value objects (Vernon)
- **Standard Types Expressed as Values** — Modeling enums and type codes as value objects

### Services

Stateless operations that don't naturally belong to entities or value objects.

| Type | Responsibility |
|---|---|
| **Domain Service** | Encapsulates domain logic spanning multiple entities/VOs |
| **Application Service** | Coordinates use cases, delegates to domain layer |
| **Infrastructure Service** | Technical capabilities (email, file storage, etc.) |

- **Statelessness** — Services maintain no internal state affecting behavior
- **Separated Interface** — When to extract service interfaces (Vernon)

### Modules (Packages)

Cohesive groupings of related domain concepts.

- Tell the domain's story while minimizing coupling between distinct ideas
- Names should be part of the Ubiquitous Language
- Reflect insight into the domain, not just technical organization
- **Module Naming Conventions** — Aligning names with BC and ubiquitous language (Vernon)
- **Modules in Other Layers** — Not just the domain layer
- **Module Before Bounded Context** — Modules as a stepping stone to context boundaries

## The Life Cycle of a Domain Object (Ch.6)

### Aggregates

Clusters of related objects treated as a unit for data changes.

#### Core Concepts

- **Aggregate Root** — The single entity through which all external access occurs; has global identity
- **Aggregate Boundary** — Defines what is inside the aggregate
- **Invariants** — Consistency rules that must be maintained within the aggregate at all times
- **Transactional Consistency** — Everything within an aggregate boundary is consistent after each
  transaction

#### Evans' Aggregate Rules

1. Root entity has global identity; internal entities have local identity only
2. Nothing outside the aggregate boundary holds a reference to anything inside except the root
3. Only aggregate roots can be obtained directly via database queries; everything else by traversal
4. A delete operation must remove everything within the aggregate boundary at once
5. When a change to any object within the boundary is committed, all invariants of the whole
   aggregate must be satisfied

#### Vernon's Four Rules (IDDD)

| Rule | Description |
|---|---|
| **Rule 1** | Model True Invariants in Consistency Boundaries — only modify one aggregate per transaction |
| **Rule 2** | Design Small Aggregates — ~70% are just root + VOs; ~30% have 2-3 entities |
| **Rule 3** | Reference Other Aggregates by Identity — use IDs not direct object references |
| **Rule 4** | Use Eventual Consistency Outside the Boundary — publish domain events for cross-aggregate updates |

- **Don't Trust Every Use Case** — Not every UI requirement should shape aggregate design
- **Reasons to Break the Rules** — Pragmatic exceptions with documentation (ADRs)
- **Model Navigation** — Traversing between aggregates via identity lookup
- **Scalability and Distribution** — Small aggregates enable distribution

### Factories

Encapsulated creation mechanisms for complex objects and aggregates.

- **Factory Methods** — Construction logic on aggregate roots or services
- **Abstract Factory Classes** — Determine concrete subtypes needed
- **Builder Classes** — Handle intricate multi-step assembly
- **Constructors** — Reserved for trivial object creation
- **Creation vs. Reconstitution** — Factories for new objects assign new identity; reconstitution
  from persistence does NOT assign new identity
- **Invariant Guarantee** — A factory should only produce objects in a consistent state with all
  invariants satisfied
- **Factory Method on Aggregate Root** — The root creates internal entities (Vernon)
- **Factory on Service** — When creation logic doesn't belong on any aggregate (Vernon)

### Repositories

Provide access to aggregate roots, abstracting persistence.

| Type | Semantics |
|---|---|
| **Collection-Oriented** | Mimic an in-memory collection (add, remove, query) |
| **Persistence-Oriented** | Save/update semantics (e.g., for document stores) |

- **Querying** — Provide specific retrieval methods for fully instantiated objects/collections
- **Reconstitution** — Recreating persisted objects (may internally delegate to a factory)
- **Transaction Control** — Clients manage transaction scope, not the repository
- **Repository vs. DAO** — Repositories are domain-centric; DAOs are data-access-centric

### Domain Events

Something that happened in the domain that domain experts care about.

- Evans added Domain Events to his 2015 DDD Reference as a recognized pattern
- Typically **immutable**, named in **past tense** (e.g., OrderPlaced, PaymentReceived)
- Enable decoupling between aggregates and bounded contexts
- Foundation for Event Sourcing, CQRS, and Saga patterns

#### Vernon's Extensions

- **Domain Events as First-Class Citizens** — Not in Evans' original book; Vernon promotes as essential
- **Modeling Events with Aggregate Characteristics** — Events carry identity and relevant data
- **Publishing Events from the Domain Model** — Events raised within aggregates
- **Publisher/Subscriber Pattern** — In-process event handling
- **Spreading the News to Remote BCs** — Distributed event propagation
- **Messaging Infrastructure** — Message queues, topics
- **Event Store** — Persisting events for event sourcing
- **Publishing as RESTful Resources** — REST-based event feeds
- **Autonomous Services and Systems** — Event-driven decoupling
- **Latency Tolerances** — Designing for eventual consistency delays

### Validation Levels (Vernon)

| Level | Scope |
|---|---|
| Attribute-level | Individual field validation |
| Object-level | Cross-field relationship validation |
| Aggregate-level | Multiple object orchestration validation |

### Entity Lifecycle

```
Creation (Factory) → Active Use (Domain Operations) → Persistence (Repository)
    → Reconstitution (Repository/Factory) → Archival/Deletion
```
